# Three languages

English, European Portuguese and French, in both apps, switchable at any time
without a reload and without a round trip to the server.

The whole mechanism is about eighty lines and has no dependency. What follows
is why it is shaped this way.

## English is the source, and the compiler enforces the rest

`packages/ui/src/lib/strings/en.ts` is a plain object. `pt.ts` and `fr.ts` are
typed `Dictionary`, which is `Record<keyof typeof en, Phrase>`.

That one line is the whole quality control: **add a key to `en.ts` and the build
fails until both translations exist.** No runtime fallback that silently shows
English to somebody who does not read it, no "missing translation" placeholder
that ships to a customer, no spreadsheet round-trip that goes stale. If it
compiles, all three languages are complete.

## Plurals are data

```ts
'urgency.overdue': { one: '1 overdue', other: '{count} overdue' },
```

Called as `t('urgency.overdue', { count: n })`. The language decides which form
that is, not the call site:

| | 0 | 1 | 2 |
|---|---|---|---|
| English | other | one | other |
| Portuguese | other | one | other |
| **French** | **one** | one | other |

French counts zero as singular — *0 jour*, not *0 jours*. A ternary in a
component cannot know that, which is exactly why there are no ternaries in
components. The same rule kills `` `${n} item${n === 1 ? '' : 's'}` ``: an
English plural 's' bolted on in code is untranslatable by construction.

## Sentences are never assembled

The one rule that matters more than the rest. This is forbidden:

```tsx
{t('showing')} {count} {t('of')} {total}      // no
```

because word order is not universal and neither is where the number goes. One
key, one sentence:

```tsx
{t('admin.tasks.showing', { count, total })}  // 'Showing {count} of {total}'
```

`tools/i18n.mjs` fails the build on a literal string left in a JSX text node or
a text-carrying prop, which catches the other half of the problem: text that
never reached `t()` at all.

## Dates are not sentences

Month names, weekday names and relative phrases live in `format.ts`, not in the
dictionaries, because they are structured data with their own grammar:

```
Wednesday, 4 March 2026        en
quarta-feira, 4 de março de 2026   pt — the two "de" are not optional
mercredi 4 mars 2026           fr — no comma at all
```

`format.ts` holds the language in a module variable, set by `LanguageProvider`
in a layout effect — the same shape as the business timezone, and for the same
reason: these functions are called from render paths, list builders and sort
comparators, where threading a hook would buy nothing.

Three details that are easy to get wrong and are handled:

* **Cadence.** *every 3 months* / *a cada 3 meses* / *tous les 3 mois* — but
  *tou**tes** les 3 semaines*, because *semaine* is feminine. And the singular
  is irregular in both: *todos os dias*, *tous les jours*.
* **Weekday initials** on the workload chart. English takes the first letter of
  "Wed". Portuguese cannot: *segunda, terça, quarta* all start differently from
  their initials, so the calendar convention D S T Q Q S S is a separate array.
* **Numbers.** French puts a space before `%`; Portuguese and French use a
  comma as the decimal separator, so a photo is *1,4 MB*.

## The server has exactly one language

The server speaks English — that is what it logs, and what an audit entry
records. But an error a person reads has to be in their language, so every
user-facing error carries a translation key alongside its English message:

```js
throw badRequest('VALIDATION', `${spec.label} is required.`,
  { field: spec.field, key: 'server.required', params: { fieldKey: spec.key } });
```

`errorMessage(t, err)` resolves it, in three fallbacks: the specific key the
server named, then a general sentence for the machine code (`error.VALIDATION`),
then the server's English — which is better than a shrug if a client is older
than the server it is talking to. Some keys nest: `server.required` needs a
field name, so `fieldKey` is translated before it is substituted.

This also fixed something else. `need(value, 'Equipment type')` used to throw
`{ field: 'Equipment type' }` while the form looked for `field === 'typeId'`, so
required-field errors highlighted nothing. The field name and the label are now
separate, because they always were.

## Choosing a language

Detection is `localStorage`, then `navigator.languages` in preference order,
then English. It is stored per app (`mm.admin.lang`, `mm.worker.lang`) next to
the theme, because it is a per-device display preference and not business data —
the same reasoning the theme already followed.

It is reachable in three places, and one of them is the point:

* **On the sign-in screen of both apps.** Somebody who cannot read English must
  be able to switch *before* authenticating, not after.
* **In the admin account menu** — a compact EN / PT / FR segment with a pill
  that slides.
* **In the worker's account sheet**, as full-width 56px rows showing each
  language by its own name — *Português*, never *Portuguese*. A dropdown
  labelled "Language" in a language you do not read is not a way out.

`<html lang>` follows the choice, so screen readers switch voice and
hyphenation follows the right rules.

## The phone is the hard case

Portuguese and French run 15–30% longer than English, and the worker app is
used one-handed, outdoors, on a phone. So the layout is not assumed — it is
measured. `node tools/i18n.mjs` loads every screen in all three languages at
402px and 1440px and reports anything whose content is wider than its box, plus
any page that scrolls sideways at all.

Deliberate truncation is not a failure: an asset name cut with an ellipsis is
data, and cutting it is the design. Content escaping a box that was never meant
to scroll is a failure, and the tool names the element and by how many pixels.
